# 第6章 移动端巡查与传统村落木构损伤规划应用

## 6.1 移动端巡查系统总体设计

第4章完成了木构损伤目标检测方法论和模型算法实验的讨论，第5章进一步获得了损伤区域的像素级边界和表观几何量。为了便于现场使用，本文将检测模型部署到 Android 移动端，形成集图像采集、损伤识别和结果整理于一体的巡查工具。系统总体流程如图6-1所示：首先利用训练得到的模型完成检测，然后将模型转换为 NCNN 格式并嵌入 Android 应用，最后在移动端输出检测图像和巡查报告。对于需要精细量化的结果，再将照片和检测记录转入离线处理流程。

![图6-1 移动巡查、离线量化与GIS应用总体架构](../../../../outputs/thesis/chapter6/fig6-1_overall_architecture.svg)

系统主要包括三个部分。第一部分是移动采集端，负责调用摄像头获取现场图像，并显示检测框、损伤类别和置信度。第二部分是检测与结果整理端，负责模型推理、检测结果绘制、照片保存和报告生成。第三部分是后续分析端，用于结合第5章的分割量化结果以及建筑、构件等巡查信息进行整理。三部分之间通过原始照片和检测记录连接，便于后续复核和再次处理。

移动端检测结果表示木材表面的可见异常，不能直接等同于木材内部腐朽程度或建筑结构安全等级。现场应用中，模型结果作为巡查人员发现问题和安排复查的辅助信息，最终判断仍需结合构件位置、损伤范围和专业人员现场检查。

## 6.2 Android应用功能与界面

### 6.2.1 功能组成

Android应用fork于腾讯优图实验室（Tencent Youtu Lab）开源项目ncnn，ncnn 是一个面向移动端、嵌入式和桌面端部署优化的高性能神经网络推理框架，无第三方运行时依赖，支持 CPU 和 Vulkan GPU 后端，并提供 pnnx 等工具将 PyTorch 和 ONNX 模型转换为 ncnn 模型。本项目构架采用 Kotlin/Java 应用层、JNI/C++ 原生层和 NCNN 推理层的结构。应用首页提供实时巡检、照片分析和报告生成三个入口。实时巡检通过 Camera2 NDK 获取摄像头画面，在预览界面上叠加检测结果；照片分析支持选择多张照片并依次检测；报告生成页面将检测照片和识别文字整理为可阅读的检测报告。

应用使用的检测类别包括开裂、深层腐朽、虫害、霉变、表面腐朽和木节。实时检测适合现场快速查看，照片分析适合对已经拍摄的影像进行集中处理，报告页面则用于保存巡查结果和辅助后续整理。

### 6.2.2 应用界面与检测结果

图6-7展示了应用的主要界面和检测结果。首页提供三个功能入口；照片检测页面显示待检测照片及检测框；报告页面可以输入检测地点并生成文字结果。已有检测示例中，系统对木材表面的裂缝、霉变和表面腐朽给出了类别和置信度，说明移动端应用已经形成了从图像输入到结果展示的基本流程。

![图6-7 移动端应用界面及木构损伤检测结果](../../../../outputs/thesis/chapter6/fig6-7_mobile_app_results.svg)

在 Xiaomi 21091116AC 手机上进行实时运行测试时，CPU 后端的 `detect()` 平均耗时约36.8 ms，Vulkan 后端平均耗时约80.5 ms；用户在实时预览界面观察到的刷新速度约为15 FPS。运行过程中，CPU 后端进程 PSS 约145 MB，Vulkan 后端约191 MB。上述结果表明当前应用能够完成现场检测流程，实际使用时优先采用 CPU 后端更为合适。

### 6.2.3 端侧测试结果

为了解移动端模型的运行情况，本文在 Xiaomi 21091116AC 手机上分别测试了 NCNN CPU 和 Vulkan 后端，输入尺寸为640×640，模型为 `yolo11s.ncnn`。测试结果见表6-1。

| 后端 | 平均推理延迟/ms | 最大推理延迟/ms | 日志窗口吞吐/FPS | 进程PSS/MB | Native Heap/MB | CPU采样占用 |
|---|---:|---:|---:|---:|---:|---:|
| NCNN CPU | 36.80 | 127.53 | 约24.2 | 145.04 | 85.44 | 约6% |
| NCNN Vulkan | 80.53 | 349.19 | 约12.2 | 191.37 | 126.19 | 约7% |

用户在实时预览界面观察到的应用刷新速度约为15 FPS，约对应66.7 ms/帧。该数值反映相机采集、推理和界面绘制共同形成的实际刷新表现；表6-1中的推理延迟只统计 `detect()` 过程。可以看出，在本次设备和模型配置下，CPU后端的平均推理速度约为Vulkan后端的两倍，且内存占用更低，因此实时巡查采用CPU后端更为合适。Vulkan后端虽然提供了GPU计算路径，但对于当前规模较小的模型，GPU调度开销使其没有表现出速度优势。

## 6.3 NCNN移动端部署

### 6.3.1 模型转换与应用架构

本文采用 NCNN 作为移动端推理框架。NCNN 以 C++ 实现，支持移动 CPU 和 Vulkan 计算，并使用 `.ncnn.param` 和 `.ncnn.bin` 文件保存网络结构与模型参数。模型转换和移动端运行的整体关系如图6-2所示。

![图6-2 NCNN移动端部署架构与模型转换流程](../../../../outputs/thesis/chapter6/fig6-2_ncnn_pipeline.svg)

模型经过 TorchScript、PNNX 和 NCNN 转换后，放入 Android 工程的 assets 目录。应用层负责页面交互和图像管理，JNI 层负责 Bitmap 与 OpenCV 图像之间的转换，NCNN 层负责网络加载和前向推理。对于连续相机画面，原生层直接接收 Camera2 NDK 输出的图像帧，从而减少 Java 层图像复制带来的额外开销。

### 6.3.2 移动端推理过程

移动端单帧推理过程如图6-6所示。摄像头首先提供当前图像帧，程序对图像进行等比例缩放和填充，使其符合模型输入尺寸；随后由 NCNN 完成前向计算，经过候选框解码和非极大值抑制得到最终检测框，最后将输入坐标还原到原始画面并绘制到界面上。

![图6-6 移动端单帧推理流程](../../../../outputs/thesis/chapter6/fig6-6_mobile_inference_flow.svg)

当前应用模型文件大小约为18.88 MB，debug 安装包大小约为65.05 MB。测试设备上 CPU 后端的检测速度高于 Vulkan 后端，原因在于当前模型规模较小，GPU 调度和数据传输开销抵消了并行计算带来的收益。该现象属于本次设备测试结果。从模型结构估算，当前 `yolo11s` 在512×512输入下的理论计算量约为21.5 GFLOPs

## 6.4 结构化损伤事件输出

### 6.4.1 事件记录方法

为了便于整理多张照片的检测结果，本文将一次检测到的单个损伤目标定义为一个损伤事件。事件记录以照片为基本来源，保存检测类别、置信度和复核状态，并预留建筑编号、构件编号、坐标和像素位置等字段。这样既能保留模型原始输出，也能在人工检查后补充现场信息。

事件表的核心字段如下：

| 字段 | 含义 |
|---|---|
| `event_id` | 单个损伤事件的唯一编号 |
| `inspection_id`、`photo_id` | 巡查任务和原始照片编号 |
| `class_pred`、`confidence` | 模型预测类别和置信度 |
| `box_xyxy_px` | 检测框在原图中的像素坐标 |
| `building_id`、`component_id` | 建筑和构件编号 |
| `lon`、`lat` | 照片或人工核验后的空间位置 |
| `review_status` | 人工复核状态 |

### 6.4.2 输出示例

根据现有应用报告页面整理的结构化输出示例见 `outputs/thesis/chapter6/structured_event_output/`。其中一次巡查包含3张照片和6条候选事件：第1张照片识别出3处开裂，第2张照片识别出2处霉变，第3张照片识别出1处表面腐朽。事件表同时保存照片编号和置信度，使检测结果能够从报告图片还原为可检索的记录。

![图6-3 巡查影像、损伤事件、构件与建筑的数据关系](../../../../outputs/thesis/chapter6/fig6-3_data_model.svg)

示例事件表中的建筑编号、构件编号和坐标暂未填写，后续巡查时可以由工作人员根据现场台账补录。模型结果和人工复核结果分开保存，人工确认类别或排除误检时不覆盖原始预测值。同一构件被多次拍摄时，系统保留各张照片中的原始事件，并通过重复标记或人工合并记录处理重复问题。

## 6.5 现场应用与巡查规划

移动端应用适合用于传统村落木构建筑的现场初筛。巡查人员可以先通过实时模式观察构件表面，再使用照片分析模式保存重点部位的检测结果。对于置信度较低但现场表现明显的目标，可以重新拍摄或交由人工复核；对于多张照片中反复出现的同一位置，可以在事件表中进行关联。

在巡查安排中，可将检测类别、置信度、表观范围、照片质量和人工复核结果作为排序依据。检测结果较明确且位于重要构件的记录可优先安排复查；置信度较低或图像模糊的记录则优先补拍。图6-5给出了基于紧迫性和可靠性的复查优先级表达方式。

![图6-5 证据紧迫性—可靠性二维复查优先级矩阵](../../../../outputs/thesis/chapter6/fig6-5_priority_matrix.svg)

这种排序方式能够把模型输出转化为巡查工作的先后顺序，但不直接给出建筑结构安全等级。建筑价值、使用状况、构件重要性和维修条件等信息，仍需由专业人员结合传统村落保护要求进行判断。

## 6.7 本章小结

本章面向传统村落木构建筑巡查需求，设计并实现了基于 Android 和 NCNN 的移动端检测应用。系统能够完成实时检测、照片分析、结果保存和报告生成，并通过 JNI 将相机图像传递至 NCNN 推理层。真机测试表明，当前设备上 CPU 后端的检测速度优于 Vulkan 后端。

在此基础上，本文将单个检测目标整理为结构化损伤事件，记录照片来源、损伤类别、置信度和人工复核状态，并预留建筑、构件及空间信息字段。该数据组织方式连接了移动端检测结果与后续人工巡查、GIS 管理和离线量化处理，为木构建筑损伤信息的持续积累提供了统一格式，辅助现场发现和复查排序。
